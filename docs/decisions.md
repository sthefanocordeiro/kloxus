# Decisions

Running log of implementation decisions. When the spec is ambiguous, choose the
simplest option that keeps the zero-setup demo working and record it here.

| # | Date | Decision | Rationale |
| --- | --- | --- | --- |
| D1 | 2026-11-09 | SQLite via `modernc.org/sqlite` (pure Go, no CGO) instead of the PostgreSQL named in the README architecture table. In-process `jobs` table + ticker instead of a Postgres queue. | Judges must run the project with only Go installed; no external services allowed. README's architecture section is updated in M6. |
| D2 | 2026-11-09 | Demo mode is the default and runs fully offline: fixture feeds, replayed LLM responses, `.eml` files in `./outbox`, fake payment provider. | No API keys or accounts may be required to evaluate the project. |
| D3 | 2026-11-09 | Replay fixtures are keyed by a stable hash of (model, prompt template name, normalized input). Missing key = hard failure naming the key. | Makes fixtures deterministic and regenerable via `kloxus record`. |
| D4 | 2026-11-09 | The Anthropic client is built in milestone 2, before the `record` command is polished in milestone 4. | Replay fixtures can only be produced by real API calls; M2 cannot finish without them. |
| D5 | 2026-11-09 | Model IDs are configurable env vars. The spec's `claude-haiku-5-5` / `claude-sonnet-5-5` are placeholders to be verified against the API at integration time. | Model naming changes; never hard-code. |
| D6 | 2026-11-09 | All UI assets (CSS, htmx) are embedded with `go:embed`. No CDN links. | The UI must work offline. |
| D7 | 2026-11-09 | ~~No hosted deployment for the MVP~~ **Revised 2026-11-10:** a publicly hosted demo IS required — HackBrazil rules demand a working demo link that stays up through evaluation. We deploy the demo-mode binary itself to fly.io/VPS; the product remains fully self-hostable. | Submission rules §7.2–7.3 supersede the original spec's "no hosted server" assumption. The demo-mode build is ideal for hosting: replayed fixtures, embedded SQLite, zero keys, deterministic output. |
| D10 | 2026-11-10 | Rejected re-architecting the demo to serverless + Postgres/Supabase (Vercel/Netlify path). Postgres is deferred to the post-pilot SaaS phase. | Serverless can't run a persistent process with a writable FS; would need dual SQL dialect, function adapter, timeout chunking, and Supabase free tier pauses after ~7 days idle — a mid-evaluation outage risk. ~2–4 days of work for zero judge-visible gain. |
| D11 | 2026-11-10 | Interactive-path LLM calls (editorial-guide rebuild, "alternative" suggestions) get deterministic fallbacks when no replay fixture matches; pipeline-path calls (triage…citecheck) fail loudly instead. | Judge interactions are arbitrary input — no fixture can cover them. The fallback keeps the demo honest and working; real mode always uses the model. |
| D12 | 2026-11-10 | Deep dive is a single batched model call in demo mode (top-3 items); the per-item bounded tool loop is real-mode only. | A demo tool loop would need recorded tool outputs, doubling fixture surface for no visible gain. |
| D13 | 2026-11-10 | `stories` are rebuilt from scratch every run; old `issue_items` keep a dangling `story_id`. | Dedupe output must be identical across runs for replay keys to stay stable. Old issues are self-contained in `dossiers` and `body_md`. |
| D14 | 2026-11-10 | Firecrawl integration: `/monitor` API for `type: page` sources without RSS (real mode), `scrape` endpoint stays the immediate-fetch fallback; `MonitorProvider` interface with a simulated demo badge; webhook `POST /webhooks/firecrawl` + "Check now" polling fallback for localhost. | Firecrawl sponsors HackBrazil (5,000 credits). The original spec scoped it to extraction only because no hosted server was assumed; with a public instance, monitoring is the better fit. Crawl/website monitors stay out of scope. |
| D15 | 2026-11-10 | In replay mode, PhaseB sends the canonical all-selected item set to draft/citecheck regardless of review decisions, then filters the stored body and flags to non-rejected items. Real mode keeps active-only input. | Judge decisions are arbitrary and must not change fixture keys. The canonical prompt reuses the recorded full-issue draft/citecheck responses while preserving the editor's selected issue. |
| D16 | 2026-11-10 | Demo reset is serialized against pipeline runs with a `sync.RWMutex` (runs take read lock, reset takes write lock), and `DB.Reset` clears `sqlite_sequence` so the reseeded publication always gets id 1. | A hosted reset must not wipe data mid-run; stable ids keep deep links (`/pub/1/...`) valid across resets without a config-level id. |
| D8 | 2026-11-09 | Reader payments go through the creator's own AbacatePay account; Kloxus stores a restricted, AES-256-GCM-encrypted key and never holds money. | Editorial principle: readers pay the creator, not us. |
| D9 | 2026-11-09 | Fixture articles are fictional and original, written for this repo, with fictional outlets. No real article text is committed. | License safety and a clear conscience for the curation-is-not-reproduction principle. |
| D17 | 2026-11-11 | Hosted demo runs multi-workspace: `KLOXUS_DATA_DIR` switches to one SQLite file per visitor (signed-cookie id), cloned from a seeded `template.db`; LRU handle cache + idle-age cleanup + per-IP create rate limit. | Each judge gets an isolated, persistent demo without accounts; a reset affects only that workspace. |
| D18 | 2026-11-11 | Visitor-added sources are stored but never fetched in demo mode; `FixtureFetcher` is the only fetcher and collect skips non-`fixtures/` URLs. | Public-source-addition on a public instance is an SSRF surface; simulation keeps the feature visible and safe. |
| D19 | 2026-11-11 | Fixture content is fully fictional (Valdória: BCV, Lume, Autoridade da Concorrência, Universidade de Porto Alto, Consórcio Lumen) on reserved `.example` domains; article links are served by the app at `/a/{item}`. A denylist test (`TestFixturesAreFictional`) guards it. | Demo must not present real institutions/companies/people as covered news; app-served articles keep every link clickable offline. |
| D20 | 2026-11-11 | Issue body stores only reader content (no score/reason/commentary placeholders); commentary lives in `issues.commentary_json` and `delivery.ReaderBody` composes the final output per surface. Internal data is filtered deterministically, never by prompt promises. | Reader-facing output must never leak review metadata or helper text. |
